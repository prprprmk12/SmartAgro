# SmartAgro AI Advisor

Веб-dashboard для учёта полей Акмолинской области, просмотра погоды, индексов и затрат хозяйства. Индексы можно получить по запросу из CDSE или загрузить из CSV. Исторический ориентир урожайности рассчитывается по прошлым сезонам; калиброванная погодная модель и автоматическое обновление по расписанию ещё не подключены.

## Запуск

```powershell
npm install
npm run dev:full
```

Укажите `DATABASE_URL` PostgreSQL в локальном `.env`, затем откройте `http://localhost:5173/`. Backend не запускается без PostgreSQL — временная база в памяти больше не используется.

Можно запускать отдельно:

```powershell
npm run server   # API на http://localhost:3001
npm run dev      # frontend на http://localhost:5173
```

Production-проверка:

```powershell
npm run build
```

## Публикация на Railway

Один Railway-сервис запускает Express API и отдаёт собранный frontend с того же домена. Отдельный frontend-сервис и `VITE_API_URL` не нужны.

1. Добавьте в проект Railway сервис **PostgreSQL**. Приложение начинает работу с чистой базой и не обращается к прежнему хранилищу.
2. Для сервиса приложения в **Variables** задайте `DATABASE_URL=${{Postgres.DATABASE_URL}}` (сверьте название сервиса в Railway) и `NODE_ENV=production`. PostgreSQL доступен приложению по приватной сети Railway.
3. Карта Leaflet по умолчанию использует спутниковую подложку [Esri World Imagery](https://www.arcgis.com/home/item.html?id=10df2279f9684e4a9f6a7f08febac2a9) с прозрачным слоем [World Boundaries and Places](https://server.arcgisonline.com/ArcGIS/rest/services/Reference/World_Boundaries_and_Places/MapServer?f=pjson) для названий городов; рядом есть режим [OpenTopoMap](https://opentopomap.org/about) с рельефом и данными OpenStreetMap/SRTM. Новый API-ключ для этих подложек не нужен. Если спутниковые тайлы недоступны, карта сообщает об этом и показывает OpenTopoMap. При недоступности OpenTopoMap остаётся стандартная OpenStreetMap с явным предупреждением. На карте отображается атрибуция каждого источника, включая лицензию стиля OpenTopoMap CC BY-SA.
4. Для настоящего AI-анализа фотографий создайте [OpenAI API key](https://platform.openai.com/api-keys) с доступом к API и задайте `OPENAI_API_KEY` в Variables backend-сервиса; при необходимости задайте `OPENAI_MODEL` (по умолчанию `gpt-4o-mini`, поддерживающая изображения). Подписка на ChatGPT не заменяет доступ и лимиты OpenAI API. Ключ используется только сервером. Без него текстовый чат работает в rule-based режиме, **но компьютерный анализ фото не выполняется**.
   Чтобы получать спутниковые индексы по кнопке из CDSE, добавьте `CDSE_CLIENT_ID` и `CDSE_CLIENT_SECRET` **только в Variables backend-сервиса**. Получите OAuth Client в [CDSE Sentinel Hub Dashboard](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub/UserGuides/BeginnersGuide.html) (User Settings → OAuth Clients). Не используйте обычный пароль учётной записи.
5. Railway прочитает `railway.json`: Railpack установит зависимости по `package-lock.json`, выполнит `npm run build`, затем `npm start`. В разделе **Networking** сгенерируйте публичный домен. Проверьте главную страницу и `https://<домен>/api/health` (режим `postgresql`). Если в Railway вручную задана команда сборки, установите `npm run build` или удалите переопределение.

При переходе на новую пустую базу зарегистрируйтесь заново: прежние аккаунты и поля в ней отсутствуют. Если браузер хранит старый токен, приложение удалит его после `401` и покажет экран входа. `401` при попытке входа означает, что аккаунта с этой почтой и паролем в текущей PostgreSQL нет или данные введены неверно. `400` при регистрации содержит конкретную причину в JSON-ответе; `403` при попытке вступить в существующее хозяйство означает, что нужен действующий код приглашения на этот email.

По [тарифам Railway](https://docs.railway.com/pricing/plans), указанные на Free/Trial **1 ГБ** — это временный диск (и на Trial 1 ГБ RAM), а объём постоянного тома базы — **0,5 ГБ**. При заполнении тома PostgreSQL запись данных остановится: следите за использованием постоянного тома.

После новой регистрации поля и расходы сохраняются в PostgreSQL выбранного хозяйства. При повторном входе с другого устройства они загружаются через `/api/fields`. Браузерные записи локального режима не добавляются в новую PostgreSQL автоматически.

### Фото вне PostgreSQL

Для загрузки новых фотографий создайте [приватный Railway Storage Bucket](https://docs.railway.com/storage-buckets) и задайте в **Variables сервиса приложения** ссылки на его Credentials (замените `Photos` на имя вашего bucket-сервиса):

```env
S3_ENDPOINT=${{Photos.ENDPOINT}}
S3_REGION=${{Photos.REGION}}
S3_BUCKET=${{Photos.BUCKET}}
S3_ACCESS_KEY_ID=${{Photos.ACCESS_KEY_ID}}
S3_SECRET_ACCESS_KEY=${{Photos.SECRET_ACCESS_KEY}}
```

Для старого bucket с path-style URL дополнительно установите `S3_FORCE_PATH_STYLE=true`, как указано в его Credentials. Если Railway Bucket недоступен на вашем тарифе, можно указать другой приватный S3-совместимый сервис через те же переменные. Секреты не добавляются в frontend и git. Если bucket не настроен, новые фото не записываются в PostgreSQL: API вернёт понятную ошибку, при этом поля без фото остаются доступны. Bucket тарифицируется отдельно от тома PostgreSQL.

Backend проверяет изображение (JPG, PNG, WEBP, до 5 МБ), загружает его в приватный bucket, а в PostgreSQL хранит только ссылку вида `asset:<hash>`. Просмотр фото доступен пользователю своего ТОО через короткоживущую подписанную ссылку; при истечении ссылки клиент запрашивает новую. AI-анализ ранее сохранённого фото также проверяет принадлежность поля. Изображения, которые **уже** лежали в полях PostgreSQL как base64, остаются там до переноса: после настройки bucket владелец открывает **Профиль → Перенести старые фото**. Операцию можно повторить; завершённые фото сохраняются как ссылки. Контент bucket не является публичным. Удаление фото из карточки пока удаляет ссылку в поле, но не очищает объект в bucket автоматически.

### AI-анализ фото

Фотоанализ доступен **только для сохранённого поля**. Откройте редактирование поля, загрузите до пяти снимков и нажмите **«Проанализировать фото»**. Чтобы сохранить результат и снимки в истории, затем нажмите **«Сохранить изменения»** — для сохранения необходим приватный Storage Bucket. Если bucket ещё не настроен, можно проанализировать только новые снимки прямо из браузера; вывод будет виден в форме, но **не сохранится в PostgreSQL**. Ранее сохранённые фото-ссылки без bucket прочитать нельзя. Нужен действительный `OPENAI_API_KEY` в Variables сервиса приложения Railway и доступ к выбранной vision-модели; при необходимости можно использовать отдельный `OPENAI_VISION_API_KEY`. `GET /api/ai/status` показывает наличие ключа, название модели и хранилища — реальный доступ к OpenAI проверяется при запросе.

Если OpenAI отклонил ключ (`HTTP 401` у внешнего сервиса), исчерпал лимит (`429`) или не принимает модель/изображение (`400`), API фотоанализа возвращает **ошибку с причиной и `requestId`**, а не демонстрационный текст. Сессия SmartAgro при ошибке ключа OpenAI не завершается. В Railway Logs найдите `Photo analysis failed` с указанным `requestId`; не публикуйте сам ключ и содержимое фото. Работа текстового чата без ключа отличается от анализа изображений.

Погода запрашивается сервером у Open-Meteo по координатам выбранного поля (`GET /api/weather?field_id=...`, требуется вход), включает 7 дней и время получения. Последний полученный прогноз хранится в PostgreSQL: если Open-Meteo недоступен, остаются только ещё не прошедшие дни с пометкой о сохранённом прогнозе. Если пригодных данных нет, отображается ошибка без вымышленных показателей. Индексы доступны после расчёта в CDSE или загрузки измерений с источником (см. ниже). Исторический ориентир урожая строится только при наличии истории той же культуры. Калиброванная сезонная модель урожая и климатические индексы риска пока не подключены.

### Загрузка NDVI / EVI / NDWI

Выберите сохранённое поле и нажмите **Загрузить CSV** в блоке индексов. В интерфейсе можно скачать пустой шаблон. Формат: `date,index,value,source,cloudCoverPct` — последняя колонка необязательна; разделитель запятая или точка с запятой. Например, `date` задаётся как `YYYY-MM-DD`, `index` — `ndvi`, `evi` либо `ndwi`, `value` — число от −1 до 1, `source` — указание реального поставщика/продукта, `cloudCoverPct` — 0–100. Файл должен содержать **уже полученные измерения среднего значения по полю**: при загрузке CSV приложение не рассчитывает их заново и не проверяет происхождение файла. Не загружайте произвольные значения как спутниковые данные.

После загрузки данные сохраняются в PostgreSQL для конкретного поля и ТОО. Повторная загрузка строки с теми же датой, индексом и источником обновляет измерение. API: `POST /api/fields/:fieldId/indices/import` с JSON `{"measurements":[{"date":"YYYY-MM-DD","index":"ndvi","value":0.5,"source":"имя поставщика","cloudCoverPct":10}]}`; `GET /api/fields/:fieldId/indices?index=ndvi&period=30d` поддерживает периоды 7d, 30d и 90d. Оба маршрута требуют входа. Карта показывает среднее значение выбранного индекса **для всего поля**, а не растровые зоны внутри поля; при отсутствии измерений показывает «Нет данных». График и HTML-отчёт используют только загруженные значения с датами и источниками.

### Получение из CDSE

Для сохранённого поля с **точным нарисованным контуром** нажмите **Обновить из CDSE** в блоке индексов. Backend переводит координаты полигона в метрическую проекцию EPSG:3857 и отправляет его в [CDSE Sentinel Hub Statistical API](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub/Statistical/Examples.html), получает статистику Sentinel-2 L2A за последние 30 дней и сохраняет средние NDVI, EVI и NDWI в PostgreSQL. Используются каналы B02, B04, B08 и B11; NDWI здесь — индекс влаги растительности `(B08 − B11)/(B08 + B11)`. В расчёт входят только классы SCL «растительность» и «голая почва»; облака, тени, снег, вода и пиксели без данных исключаются. Шаг сетки соответствует приблизительно 20 м на местности на широте поля. Дневные интервалы с менее чем 30% валидных пикселей или без измерений пропускаются. Процент валидных пикселей **не равен** точной облачности сцены.

`POST /api/fields/:fieldId/indices/sync` требует сессии и проверяет принадлежность поля ТОО. Повторный запрос по тому же контуру доступен не чаще одного раза в 6 часов, чтобы беречь [квоту CDSE](https://documentation.dataspace.copernicus.eu/Quotas.html). При изменении контура старые расчёты CDSE для него больше не отображаются — обновите данные повторно. При недоступности CDSE сохранённые ранее значения остаются, новые не выдумываются. Дата измерения — начало дневного интервала Statistical API, **не точное время отдельного снимка**. Спутниковая подложка Esri — отдельная мозаика изображений; дата её съёмки может отличаться от даты расчёта CDSE. Интеграция CDSE даёт среднее по полигону и график, но пока не загружает растровую карту внутриполевых зон и не выполняет обновление по расписанию.

Если CDSE возвращает ошибку, интерфейс и ответ `/indices/sync` показывают этап (`auth` или `statistics`), HTTP-код CDSE и безопасное описание причины; в Railway Logs ищите строку `CDSE sync failed` с тем же `requestId`. `auth`/401 означает проблему OAuth Client ID/Secret, `statistics`/400 — ошибку параметров расчёта; 429 — ограничение частоты или квота. Не отправляйте Client Secret, Access Token и полный журнал авторизации в чаты или баг-репорты.

Задачи выбранного поля доступны через `GET /api/tasks?field_id=...`, `POST /api/tasks` и `PATCH /api/tasks/:taskId`. Для всех операций требуется серверная сессия пользователя своего ТОО. В интерфейсе можно назначить задаче участок, срок, приоритет и ответственного, отметить её выполненной и вернуть в работу. Состояние сохраняется в PostgreSQL.

### История урожайности

В блоке **История урожайности** выбранного поля можно записать сезон вручную: год, культуру, посевную площадь (га), фактический сбор (т) и источник информации. Урожайность рассчитывается прозрачно: `сбор / посевная площадь`. Записи можно исправить или удалить; каждое поле хранит историю отдельно в PostgreSQL. Один год может содержать несколько культур, но одинаковую комбинацию года и культуры в одном поле нельзя добавить повторно.

Для импорта доступен пустой шаблон CSV с колонками `year,crop,plantedAreaHa,harvestTotalT,source`. Принимаются разделители `,` и `;`, до 100 строк, десятичная точка или запятая с разделителем `;`. Повторный импорт того же года и культуры обновляет запись. Источник заполняет пользователь; приложение не выдаёт эти значения за независимо проверенную статистику. API с проверкой доступа к ТОО: `GET/POST /api/fields/:fieldId/seasons`, `POST /api/fields/:fieldId/seasons/import`, `PATCH/DELETE /api/fields/:fieldId/seasons/:seasonId`.

### Исторический ориентир урожайности

`GET /api/fields/:fieldId/yield-forecast` требует входа и возвращает результат только для поля своего ТОО. Нужны минимум **три завершённых сезона той же культуры** до текущего года. Модель `historical-median-v1` использует до 10 последних таких сезонов: `prediction` — медиана фактической урожайности, `lower_bound` и `upper_bound` — 10-й и 90-й процентили **наблюдавшихся значений**, неблагоприятный/базовый/благоприятный сценарии — минимум/медиана/максимум истории. Общий сбор сценария = урожайность × текущая посевная площадь. Без трёх сезонов API возвращает `status: insufficient_data` и числа `null` с объяснением, а dashboard не показывает мнимый прогноз.

Диапазон P10–P90 **не является калиброванным 80% доверительным либо предсказательным интервалом**. Ответ содержит `confidence: low`, годовые значения и источники в `features`, ограничения, дату и версию модели. Погода, NDVI/NDWI, сроки сева и риск снега пока **не корректируют** число: для этих поправок нужны данные за прошлые сезоны и проверка точности модели. Сценарная маржа в интерфейсе использует введённые агрономом цену зерна и прямые затраты; это не обещание выручки.

Кнопка «Скачать отчёт» в dashboard формирует HTML-отчёт по выбранному полю: схему внесённого контура, историю сезонов, исторический ориентир с ограничениями, фактический сбор, загруженные индексы за 90 дней и их график (если есть измерения за разные даты), прямые затраты, погодный прогноз с датой получения и открытые задачи. HTML можно открыть в браузере и сохранить как PDF через печать. Если источника данных нет, отчёт указывает это явно; он не подставляет demo-показатели.

Проверка API полей, истории сезонов, исторического ориентира, задач, индексов, погоды, приглашений и разграничения доступа: `npm test`.

Порт Railway передаётся через `PORT` автоматически. Сервис не запустится без `DATABASE_URL`; в production также нужна собранная версия frontend. `DATABASE_URL` и `OPENAI_API_KEY` нельзя добавлять в frontend или публиковать в репозитории.

## Что доступно

- регистрация владельца нового хозяйства, вход в существующее по приглашению и сохранение полей, границ и расходов в PostgreSQL;
- спутниковая карта Esri World Imagery с подписями городов и переключаемая топографическая OpenTopoMap, создание и выделение контура поля без дополнительного API-ключа;
- фактический сбор и расчёт урожайности на основе ручного ввода агронома;
- история урожайности по сезонам с ручным вводом, исправлением и импортом CSV;
- воспроизводимый исторический ориентир урожайности при наличии трёх завершённых сезонов той же культуры с явной низкой уверенностью;
- задачи по полям: создание со сроком, приоритетом, участком и ответственным, отметка выполнения и сохранение в PostgreSQL;
- фото полей и история AI-анализов в приватном S3-совместимом bucket при настройке Railway Storage Bucket (в PostgreSQL — ссылки);
- HTML-отчёт по выбранному полю с источниками и временем формирования;
- прогноз погоды Open-Meteo на 7 дней по координатам выбранного поля, дата получения и сохранённый прогноз при сбое;
- загрузка датированных измерений NDVI/EVI/NDWI из CSV и график по выбранному полю без искусственных значений;
- получение средних NDVI/EVI/NDWI по контуру поля из CDSE Sentinel-2 L2A при настроенных OAuth-ключах;
- учёт прямых затрат и сценарная маржа по историческому ориентиру при изменении цены топлива или зерна;
- AI-чат с контекстом поля и явным сообщением об отсутствующих прогнозных данных;
- запрос геолокации пользователя для отображения его местоположения на карте.

Работа приложения требует PostgreSQL и зарегистрированного аккаунта. Локальный режим без базы больше не показывается на экране входа.

## Авторизация и PostgreSQL

До входа приложение показывает отдельный экран авторизации. Создатель нового рабочего места указывает название хозяйства и населённый пункт, после чего получает роль «Владелец». **БИН необязателен**; если он указан, сервер проверяет 12 цифр и контрольную цифру. Чтобы зарегистрироваться в существующем хозяйстве, агроному нужны **приглашение владельца и тот же email**, для которого выдан код. Простой выбор чужого хозяйства из списка больше не даёт доступа.

Владелец открывает **Профиль → Сотрудники и приглашения**, вводит рабочую почту сотрудника и передаёт появившийся код вручную. Код показывается один раз, действует 7 дней и используется при регистрации; отправки email пока нет. Там же владелец может изменить роль, отозвать неиспользованное приглашение, закрыть или восстановить доступ сотрудника. При закрытии доступа все его сессии отзываются. Кнопка выхода отзывает текущую серверную сессию. Пароли новых аккаунтов хранятся как scrypt-хеш с отдельной случайной солью.

API владельца: `GET /api/company/users`, `PATCH /api/company/users/:userId`, `GET/POST /api/company/invitations`, `DELETE /api/company/invitations/:invitationId`. `DELETE /api/auth/session` завершает текущую сессию; `GET /api/auth/me` возвращает актуальную роль. **Указанный БИН и проверка его контрольной суммы не подтверждают юридическое право представлять ТОО**: для этого потребуется отдельная интеграция с реестром или проверка документов.

Файл `.env.example` подготовлен для настройки. URI используется только backend; его нельзя размещать во frontend или коммитить в git.

Backend подключается только к PostgreSQL и создаёт таблицу `smartagro_documents`: сущности хранятся в JSONB, а поля, задачи и пользователи получают стабильные 24-символьные ID. Пустая база не содержит предсозданных хозяйств или пользователей. Зарегистрируйте владельца своего рабочего места, затем пригласите агрономов. Количество полей считается из PostgreSQL. Геолокация пользователя показывает его положение, а погода берётся только по координатам выбранного поля. Для точного отображения полей нужно нарисовать или загрузить их реальные границы; при отсутствии контура карта отмечает приблизительное положение.

## AI-чат

Ключ нельзя размещать во frontend-коде. На backend он хранится в переменной окружения:

```env
OPENAI_API_KEY=...
```

Frontend обращается к backend endpoint `/api/ai/chat`. Без ключа доступен ограниченный rule-based ответ **только для текста**; кнопка фотоанализа без OpenAI-ключа недоступна.

AI получает только данные поля пользователя из PostgreSQL, введённую агрономом историю прошлых сезонов, исторический ориентир с ограничениями, сохранённый прогноз погоды и последние измерения индексов с датой и происхождением (расчёт CDSE либо CSV пользователя). Число считает воспроизводимый backend-модуль, AI его не меняет. При недостатке истории прогнозные значения отсутствуют; происхождение CSV и истории не считается независимо проверенным. Вопросы вне работы хозяйства отклоняются.
